## Screens in scope (all live-confirmed)

There are **three distinct screens** with the payment-card/kebab-menu
widget — all three share the same underlying code and behavior (confirmed
live on all three with the same ₹2,000 test payment):

1. **Per-member payment history** — Groups tab → tap a group → tap the
   member row. Screen title is the member's name, no month selector; all
   of that member's cards across all time.
2. **"Group payments"** (matches the Figma frame's name exactly) — Groups
   tab → tap a group → tap **"Monthly Insights"** → tap a month card →
   tap **"View payments"**. Screen title is literally **"Group payments"**,
   with a month selector (e.g. "July  2026") and all members' cards for
   that month.
3. **"All payments"** (global, org-wide) — bottom nav **"Payments"** tab
   (also reachable via Home → "Dues" → "View All"). Screen title is
   literally **"All payments"**, aggregating every group's cards with no
   scoping.

Both: filter tabs All/Paid/Pending, payment cards with "Send reminder" +
"⋮" kebab menu.
Code: `lib/app/modules/payments/widgets/payment_card_bottom_actions.dart`.
3. **Confirm dialog** — "Enable partial payment?" modal.
4. **Mark As Paid screen** — Full Amount / "Enter amount" (partial) toggle
   + amount input with live validation.

## Flow (happy path — live-confirmed end to end)

1. Open either payment-card screen (per-member history, or the true
   "Group payments" screen via Monthly Insights → View payments); tap "⋮"
   on a payment card ≥ **₹2,000** (the exact confirmed threshold).
2. Kebab menu shows **4 items** (not 3, correcting the Figma-only capture):
   **Mark as paid**, **Share payment link**, **Disable**,
   **Enable Partial Payment**. `Share payment link` was not in the Figma
   frame or the original code scan — discovered live.
3. Tap "Enable Partial Payment" → confirm modal: title **"Enable partial
   payment?"** (no space before `?` — the Figma mockup's space was a design
   typo, code/live is authoritative), subtitle "Once enabled, users will be
   able to make partial payment for this payment request " (trailing space
   is real).
4. Tap Confirm → **no toast/snackbar**. Two silent, immediate UI changes:
   the card's content-desc gains a **"0%,"** prefix (a paid-percentage
   indicator), and re-opening the kebab menu shows "Enable Partial Payment"
   **already gone** — no refresh needed.
5. Opening "Mark as paid" on that order shows **"Full Amount"** and
   **"Enter amount"** (this is the live label — the code's internal
   constant name is `PARTIAL_AMOUNT`, but no "Partial Amount" text is
   actually rendered).
6. Entering an amount ≥ the pending amount shows inline error **"Amount
   should be less than 5,000"** (dynamic, reflects the actual pending
   amount) and disables **Proceed**; a lower amount enables it.

## Elements per screen

Summary status: every element in this feature is 🟢 **live-confirmed** via
`content-desc` (`AppiumBy.ACCESSIBILITY_ID`), except the raw amount
`EditText` on Mark As Paid, which has no accessible id and needs a
class/XPath fallback (lowest locator priority per `AGENTS.md`). See
page objects under `src/page_objects/cofee/` for the committed selectors.

**Merged semantics confirmed live:** payment cards expose one merged
`content-desc` block (name + group/note + amount + date) rather than
per-field labels — matches the Flutter merged-semantics pattern; there is
no separate locator for "the amount" alone on a card.

## Business rules / acceptance criteria

- **Visibility gate** (`payment_card_bottom_actions.dart:131-133`):
  `!paymentModel.isSplitPayment && subTotal >= orgConfig.splitRequiredAmountMin`.
  **Exact threshold confirmed live: `splitRequiredAmountMin = ₹2,000`,
  inclusive.** Bisected directly: ₹1,999 → option absent; ₹2,000 → option
  present.
- **Partial-amount upper bound, confirmed live:** must be strictly less
  than the pending amount; enforced with an inline error, not a toast.
- **No success feedback on enable** — confirmed live (see Flow step 4).
- **Menu item disappears immediately on enable** — confirmed live, no
  refresh/re-open needed.
- Auto-debit-in-progress block and subscription-tier gating — **not
  exercised** this round (this test account had a payment eligible without
  hitting either path); still Unknown/code-only.
- **Adjacent regression note (unchanged, still code-only):** "close
  payment" logic also branches on `isSplitPayment && totalPaidAmount > 0`.

## Edge cases / negative paths

- Partial amount ≥ pending amount → inline error "Amount should be less
  than 5,000" (dynamic message), Proceed disabled. **Live-confirmed.**
- Auto-debit in progress → blocked, error snackbar (code-only, not
  exercised live — no auto-debit-in-progress payment existed in test data).
- Subscription-plan restriction → error path exists in code
  (`.handleSubscriptionErrors()}`) but not exercised live (this account's
  plan didn't hit the restriction).
